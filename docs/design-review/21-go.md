# Design Review #21: Go's Type System vs TypeScript-Go's `identity`/`mutator`/`links`

## Document Control
- Status: Research Analysis
- Date: 2026-03-11
- Audience: TypeScript language/design contributors, checker implementers
- Scope: Cross-language comparison of Go's interfaces, concurrency primitives, and static analysis with TypeScript-Go's identity CFA system

---

## 1. Interfaces and Structural Typing

### Go's Model

Go uses implicit interface satisfaction — a type satisfies an interface if it has the required methods. No `implements` keyword exists. This is structural typing at the method-set level:

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}

type File struct { /* ... */ }

func (f *File) Read(p []byte) (int, error) { /* ... */ }

// *File satisfies Reader implicitly — no declaration needed
var r Reader = &File{}
```

This creates a "contracts through shape" philosophy: if a type has the right methods, it can be used wherever that interface is expected. The compiler checks structural compatibility at assignment sites.

### TypeScript's Structural Typing

TypeScript's structural typing operates on the same principle but at a broader surface — it checks property shapes, not just method sets:

```typescript
interface Reader {
    read(p: Uint8Array): number;
}

// Any object with a compatible `read` method satisfies Reader
const r: Reader = {
    read(p: Uint8Array) { return p.length; }
};
```

### Parallel to `identity`/`mutator`

Both Go and TypeScript-Go extend structural typing with **behavioral contracts**. In Go, the method set determines what operations are available on a type. In TypeScript-Go, `identity` and `mutator` add behavioral metadata to structural members:

| Go | TypeScript-Go | Semantic |
|----|--------------|----------|
| Interface method set | Interface with `identity`/`mutator` members | Structural contract |
| Implicit satisfaction | Structural assignability | No explicit `implements` |
| Method set rules (value vs pointer) | `identity`/`mutator` modifiers | Read vs write capability |
| Compiler-enforced at call site | CFA-enforced in flow analysis | Enforcement point |

The key shared insight: **structural contracts can encode read/write intent without nominal type hierarchies**. Go achieves this through value/pointer receiver rules (§2). TypeScript-Go achieves it through modifier keywords.

## 2. Value Receivers vs Pointer Receivers

### Go's Model

Go distinguishes between value receivers and pointer receivers on methods. This distinction is the closest direct parallel to `identity`/`mutator` in any mainstream language:

```go
type Store struct {
    data string
}

// Value receiver — cannot modify the original struct
// Receives a COPY of Store
func (s Store) Read() string {
    return s.data
}

// Pointer receiver — CAN modify the original struct
// Receives a pointer to the actual Store
func (s *Store) Write(v string) {
    s.data = v
}
```

The compiler enforces this distinction at the interface level through **method set rules**:

| Receiver Type | Method Set Includes |
|---------------|-------------------|
| `T` (value) | Only value-receiver methods |
| `*T` (pointer) | Both value-receiver AND pointer-receiver methods |

This means a value type `T` cannot satisfy an interface requiring a pointer-receiver method — the compiler prevents calling mutating methods on non-addressable values:

```go
type ReadOnly interface {
    Read() string
}

type ReadWrite interface {
    Read() string
    Write(v string)
}

var s Store = Store{data: "hello"}

var ro ReadOnly = s    // OK: Store has value-receiver Read()
var rw ReadWrite = s   // ERROR: Store does not have Write() (pointer receiver)
var rw2 ReadWrite = &s // OK: *Store has both Read() and Write()
```

### Direct Parallel to `identity`/`mutator`

| Go | TypeScript-Go | Semantic |
|----|--------------|----------|
| `func (s Store) Read() string` | `read: identity () => string` | Stable read — does not mutate |
| `func (s *Store) Write(v string)` | `write: mutator (v: string) => void` | Mutating write — invalidates reads |
| Value receiver = copy semantics | `identity` = narrowing stable | Cannot cause side effects on original |
| Pointer receiver = mutation possible | `mutator` = narrowing invalidated | Can modify underlying state |
| Interface method set rules | CFA invalidation rules | Enforcement mechanism |

```typescript
// TypeScript-Go equivalent of Go's Store
interface Store {
    read: identity () => string | undefined;   // ~ value receiver
    write: mutator (v: string) => void;         // ~ pointer receiver
}
```

### Key Difference: The Guarantee Level

Go's value/pointer distinction is a **hard guarantee** enforced by copy semantics: a value receiver literally receives a copy, so mutation is impossible (the copy is discarded). TypeScript-Go's `identity` is a **declared contract** — the checker trusts the declaration and uses it for CFA, but nothing prevents the runtime implementation from having side effects.

| Aspect | Go | TypeScript-Go |
|--------|-----|--------------|
| **Mechanism** | Copy semantics (value receiver) | Declared modifier (`identity`) |
| **Guarantee** | Physical impossibility of mutation | Trust-based contract |
| **Violation** | Cannot happen (language-level) | Runtime may violate declaration |
| **Enforcement** | Compile-time, by construction | CFA-time, by annotation |

### Interface Segregation Through Method Sets

Go's method set rules naturally create an "interface segregation" pattern that maps onto `identity`/`mutator` capabilities:

```go
// Read-only view — only value-receiver methods
type StoreReader interface {
    Read() string
    Count() int
}

// Full access — includes pointer-receiver methods
type StoreWriter interface {
    StoreReader
    Write(v string)
    Clear()
}
```

This pattern emerges organically in Go codebases (e.g., `io.Reader` vs `io.ReadWriter`). TypeScript-Go achieves the same semantic split within a single interface using modifiers rather than interface composition.

## 3. `sync.Mutex` and `sync.RWMutex` — Read/Write Locking

### Go's Concurrency Primitives

Go's `sync.RWMutex` provides the canonical read/write lock:

```go
type RWMutex struct { /* ... */ }

func (rw *RWMutex) RLock()    // Acquire read lock (shared)
func (rw *RWMutex) RUnlock()  // Release read lock
func (rw *RWMutex) Lock()     // Acquire write lock (exclusive)
func (rw *RWMutex) Unlock()   // Release write lock
```

The contract:
- **Multiple `RLock()`s can coexist** — concurrent reads are safe.
- **`Lock()` is exclusive** — no reads or writes while held.
- **`Lock()` blocks until all `RLock()`s are released** — writes wait for reads.

### Parallel to `identity`/`mutator`

| `sync.RWMutex` | TypeScript-Go | Semantic |
|----------------|--------------|----------|
| `RLock()` / `RUnlock()` | `identity () => T` | Safe concurrent/repeated reads |
| `Lock()` / `Unlock()` | `mutator (v: T) => void` | Exclusive mutation, invalidates read assumptions |
| Multiple `RLock()`s coexist | Multiple narrowed reads reusable | Reads are composable |
| `Lock()` waits for `RUnlock()` | Mutator invalidates narrowed reads | Writes reset read state |

```go
type SafeStore struct {
    mu   sync.RWMutex
    data string
}

func (s *SafeStore) Read() string {
    s.mu.RLock()         // ~ entering identity-narrowed region
    defer s.mu.RUnlock()
    return s.data        // ~ narrowed read is stable
}

func (s *SafeStore) Write(v string) {
    s.mu.Lock()          // ~ mutator call: invalidates all reads
    defer s.mu.Unlock()
    s.data = v           // ~ state changed
}
```

```typescript
// TypeScript-Go parallel:
interface SafeStore {
    read: identity () => string | undefined;
    write: mutator (v: string) => void links read;
}

if (store.read() !== undefined) {
    store.read().toUpperCase();  // ~ within RLock region — stable
    store.write("new");          // ~ Lock() — invalidates read narrowing
    store.read().toUpperCase();  // ERROR — narrowing invalidated (post-Unlock)
}
```

### The Scoping Difference

`RWMutex` uses explicit scoping (lock/unlock pairs), while TypeScript-Go uses flow-based scoping (narrowing is valid until a mutator call appears in the flow). This is a key ergonomic difference:

| Aspect | `sync.RWMutex` | TypeScript-Go CFA |
|--------|----------------|-------------------|
| **Scope mechanism** | Explicit lock/unlock pairs | Implicit flow regions |
| **Scope errors** | Deadlocks, data races (runtime) | Lost narrowing (type error) |
| **Scope granularity** | Manual, per-critical-section | Automatic, per-flow-path |
| **Developer burden** | Must pair lock/unlock correctly | Zero — CFA handles it |

TypeScript-Go's approach is strictly more ergonomic: the "lock regions" are inferred from control flow, and "lock violations" manifest as type errors rather than data races.

## 4. Channels — Directional Types as Read/Write Contracts

### Go's Channel Directions

Go channels have three forms that encode read/write capability in the type system:

```go
chan T      // bidirectional — can send and receive
<-chan T    // receive-only — can only read
chan<- T    // send-only — can only write
```

These directional types are enforced at compile time:

```go
func producer(out chan<- int) {
    out <- 42     // OK: can send
    // v := <-out // ERROR: cannot receive from send-only channel
}

func consumer(in <-chan int) {
    v := <-in     // OK: can receive
    // in <- 42   // ERROR: cannot send to receive-only channel
}

func main() {
    ch := make(chan int) // bidirectional
    go producer(ch)     // narrows to send-only at call site
    go consumer(ch)     // narrows to receive-only at call site
}
```

### Parallel to `identity`/`mutator`

Channel directions encode the same read/write contract at the type level:

| Channel Type | TypeScript-Go | Semantic |
|-------------|--------------|----------|
| `<-chan T` (receive-only) | `identity () => T` | Read capability only |
| `chan<- T` (send-only) | `mutator (v: T) => void` | Write capability only |
| `chan T` (bidirectional) | Interface with both `identity` and `mutator` | Full read/write |
| Direction narrowing at call site | CFA narrowing in flow | Contextual capability restriction |

### The `links` Analogy

Channels inherently link producers and consumers — a send on `chan<- T` invalidates assumptions about what `<-chan T` will yield next. This is precisely the `links` relationship:

```typescript
interface Channel<T> {
    receive: identity () => T;
    send: mutator (v: T) => void links receive;
}
```

The `links receive` clause makes explicit what Go's channel semantics encode implicitly: sending a value invalidates the consumer's prior knowledge about what receive will return.

### Narrowing Through Direction

Go's ability to narrow a bidirectional channel to a directional one at function boundaries is analogous to how TypeScript-Go might present different views of the same underlying state:

```go
// Go: same channel, different capabilities in different scopes
func readOnly(ch <-chan int) { /* can only receive */ }
func writeOnly(ch chan<- int) { /* can only send */ }
```

```typescript
// TypeScript-Go: same store, different capabilities via identity/mutator
interface StoreReader {
    read: identity () => string | undefined;
}
interface StoreWriter {
    write: mutator (v: string) => void;
}
interface Store extends StoreReader, StoreWriter {}
```

## 5. Type Assertions and Type Switches

### Go's Narrowing Mechanism

Go has no union types, but type assertions and type switches provide narrowing for interfaces:

```go
var i interface{} = "hello"

// Type assertion — panics if wrong
s := i.(string)

// Type assertion with check — no panic
s, ok := i.(string)
if ok {
    fmt.Println(s) // s is string here
}

// Type switch — exhaustive narrowing
switch v := i.(type) {
case string:
    fmt.Println(v) // v is string
case int:
    fmt.Println(v) // v is int
default:
    fmt.Println("unknown")
}
```

### Comparison to TypeScript CFA

| Go | TypeScript | Narrowing Mechanism |
|----|-----------|---------------------|
| `v, ok := i.(string)` | `typeof x === "string"` | Guard-based narrowing |
| `switch v := i.(type)` | `switch (typeof x)` | Exhaustive narrowing |
| Assertion `i.(string)` | `x as string` | Unsafe cast (different semantics) |
| Interface type only | Union types, discriminated unions | Scope of narrowing |

### Why Go Doesn't Need `identity` for Narrowing

Go's narrowing is limited to interface-to-concrete-type assertions and doesn't apply to value reads. Because Go has no union types, the narrowing question is always "what concrete type does this interface hold?" rather than "what value might this read return?"

TypeScript-Go's `identity` addresses a problem Go doesn't have: repeated reads from a callable that returns a union type. Go's type system is simpler here — if `Read() string` returns a `string`, it's always a `string`. There's no `string | undefined` union to narrow.

However, Go's `error` pattern creates an analogous shape:

```go
func (s *Store) Read() (string, error) {
    // ...
}

data, err := store.Read()
if err != nil {
    return err
}
// data is "narrowed" in the sense that we know err is nil
// But Go doesn't track this in the type system
data2, err2 := store.Read()
// Cannot reuse the err==nil knowledge from the first call
```

This is precisely where `identity` would help if Go had it: the second `Read()` could reuse the narrowing from the first if `Read` were declared as stable.

## 6. Generics (Go 1.18+)

### Type Parameters and Constraints

Go 1.18 introduced generics with type parameters and interface-based constraints:

```go
type Number interface {
    ~int | ~float64 | ~float32
}

func Sum[T Number](values []T) T {
    var sum T
    for _, v := range values {
        sum += v
    }
    return sum
}
```

Constraints are interfaces, and the `comparable` built-in constraint enables `==` and `!=` operations:

```go
func Contains[T comparable](slice []T, target T) bool {
    for _, v := range slice {
        if v == target {
            return true
        }
    }
    return false
}
```

### Relevance to `identity`/`mutator` Generics

TypeScript-Go's `identity` interacts with generics through constrained overloads (from the spec, §8.4):

```typescript
interface WritableSignal<T> {
    identity (): T;
    mutator update<U extends T>(fn: (value: T) => U): void;
}
```

Go's constraint system suggests a parallel for how TypeScript-Go might constrain mutator effects:

| Go Generics | TypeScript-Go | Purpose |
|-------------|--------------|---------|
| `T comparable` | `identity () => T` where T has narrowing potential | Constraining what operations are valid |
| `~int \| ~float64` (union constraint) | `T extends string \| number` | Restricting type parameter scope |
| Method constraints in interfaces | `mutator` with `links` targeting typed endpoints | Constraining write effects |

### The `comparable` Parallel

Go's `comparable` constraint is interesting because it defines a behavioral contract ("can be compared for equality") that the compiler enforces. This is conceptually similar to `identity` defining a behavioral contract ("reads are stable"):

```go
// Go: comparable constrains what T can do
func Deduplicate[T comparable](items []T) []T { /* ... */ }

// TypeScript-Go: identity constrains what CFA can assume
interface Signal<T> {
    identity (): T;  // CFA can reuse narrowing across reads
}
```

Both are **capability declarations** that unlock compiler optimizations/checks that would not be available without them.

## 7. `go vet` and `staticcheck` — Static Analysis for Stability Contracts

### Go's Static Analysis Ecosystem

Go ships with `go vet` (built-in) and the community maintains `staticcheck` (comprehensive). These tools enforce patterns that the type system cannot express:

**`go vet` checks include:**
- `copylocks`: Detects when a `sync.Mutex` is copied by value (breaks the lock)
- `loopclosure`: Detects loop variable capture bugs
- `printf`: Checks format string/argument correspondence
- `unusedresult`: Flags ignored return values of specific functions

**`staticcheck` adds:**
- `SA2001`: Empty critical section (lock immediately followed by unlock)
- `SA2003`: Deferred `Unlock` right after `Lock` with no work between
- `SA1019`: Using deprecated API
- Hundreds more domain-specific checks

### Relevant Checks for Identity/Mutator Patterns

Several existing Go static analysis checks directly parallel what TypeScript-Go's `identity`/`mutator` system enforces:

| Go Check | What It Catches | TypeScript-Go Parallel |
|----------|----------------|----------------------|
| `copylocks` | Copying a lock value (breaks exclusivity) | `identity` contract violation (copying read state with mutable backing) |
| `SA2001` (empty critical section) | Lock/unlock with no meaningful work | `mutator` call that doesn't actually mutate |
| Return value ignored | Ignoring `error` from I/O operations | Ignoring `identity` read result |
| Race detector (`-race`) | Concurrent read/write without synchronization | Mutator call interleaving with narrowed reads |

### Could Go Enforce `identity`-Like Contracts?

Go's tooling infrastructure could theoretically enforce stability contracts through custom analyzers:

```go
// Hypothetical Go analyzer annotation (not real Go syntax)
//go:identity
func (s Store) Read() string {
    return s.data // analyzer verifies: no writes to s in this method
}

//go:mutator links=Read
func (s *Store) Write(v string) {
    s.data = v
}
```

The Go analysis framework (`golang.org/x/tools/go/analysis`) provides the infrastructure for this, but Go's culture favors keeping the type system simple and using analyzer tools for advanced checks. TypeScript-Go takes the opposite approach: embedding these contracts directly in the type system.

| Approach | Mechanism | Verification |
|----------|-----------|-------------|
| Go + analyzer | Comment directives + static analysis pass | External tool, optional |
| TypeScript-Go | Language keywords + CFA | Built into checker, mandatory |
| Rust | `&` / `&mut` | Built into borrow checker, mandatory |

## 8. Alternative Syntax Ideas — Go-Inspired Patterns

### Could TypeScript Use Go's Value/Pointer Receiver Pattern?

Go's most elegant feature for read/write distinction is the receiver type. Could TypeScript-Go adopt a similar pattern?

#### Idea A: `readonly this` vs `mutable this`

Inspired by Go's `(s Store)` (value, read-only) vs `(s *Store)` (pointer, mutable):

```typescript
interface Store {
    // readonly this ≈ Go value receiver
    read(this: readonly this): string | undefined;
    // mutable this ≈ Go pointer receiver
    write(this: mutable this, v: string): void;
}
```

**Pros:**
- Leverages existing `readonly` keyword — no new keywords needed
- `this` parameter is already TypeScript syntax
- Maps cleanly onto Go's receiver semantics

**Cons:**
- `readonly this` in TypeScript currently means "this object's properties are readonly" — overloading it for CFA stability is confusing
- `mutable` is not an existing TypeScript keyword
- Doesn't express `links` (which identity endpoints does the mutation affect?)
- `this` parameter syntax is rarely used and poorly understood

#### Idea B: Directional Function Types (Inspired by Go Channels)

Go's `<-chan T` / `chan<- T` uses direction arrows. TypeScript-Go could adopt directional markers:

```typescript
interface Store {
    read: () => out string | undefined;  // "out" = read direction
    write: (v: string) => in void;       // "in" = write direction, invalidates outs
}
```

**Pros:**
- `in`/`out` already have variance meaning in TypeScript/C# — conceptual reuse
- Visually lightweight

**Cons:**
- `in`/`out` in TypeScript mean covariant/contravariant — semantic collision
- `out` on a return type is redundant (returns are always "out")
- Doesn't clearly express "stable identity" — just "direction of data flow"
- `in void` is grammatically awkward

#### Idea C: Method Set Interfaces (Go's Implicit Segregation)

Instead of per-member modifiers, separate interfaces for read and write capabilities:

```typescript
interface StoreReader {
    read(): string | undefined;  // implicitly identity by being read-only interface
}

interface StoreWriter {
    write(v: string): void;      // implicitly mutator by being write-only interface
}

interface Store extends StoreReader, StoreWriter {}
```

**Pros:**
- No new keywords at all — pure structural composition
- Go developers immediately understand the pattern
- Aligns with interface segregation principle
- Works with existing TypeScript

**Cons:**
- Doesn't give CFA any new information — a `Store` still has both read and write
- No way to express `links` between interfaces
- Forces interface explosion for complex APIs
- Doesn't solve the core problem: CFA needs to know which calls are stable reads

**Verdict:** Interface segregation is a good *design pattern* but insufficient as a *language feature*. The CFA needs explicit per-member annotations, not structural separation.

#### Idea D: Receiver Annotations (Hybrid Go/TypeScript)

Borrow Go's concept but express it through TypeScript-compatible annotations on the call site:

```typescript
interface Store {
    read: (&self) => string | undefined;  // shared/read reference
    write: (&mut self, v: string) => void; // mutable reference
}
```

**Pros:**
- Directly maps to Rust's `&self` / `&mut self` (and Go's value/pointer receivers)
- Unambiguous about mutation intent

**Cons:**
- `&self` and `&mut` are foreign syntax in TypeScript — high learning curve
- Introduces reference semantics that don't exist in JavaScript
- TypeScript doesn't have a `self` keyword
- Over-specified for a gradual type system — JavaScript has no actual reference/value distinction

### Summary of Go-Inspired Alternatives

| Approach | New Keywords | Expressiveness | Learning Curve | Verdict |
|----------|-------------|---------------|----------------|---------|
| Current (`identity`/`mutator`/`links`) | 3 | Full (read, write, selective invalidation) | Medium | Baseline |
| `readonly this` / `mutable this` | 1 (`mutable`) | Partial (no `links`) | Low | Interesting but incomplete |
| Directional `in`/`out` | 0 (reuse) | Low (no stability semantics) | Low | Too ambiguous |
| Interface segregation | 0 | Low (no CFA benefit) | None | Pattern, not feature |
| `&self` / `&mut self` | 2 | Partial (no `links`) | High | Too foreign |

**Conclusion:** Go's value/pointer receiver pattern is the most elegant read/write split in any mainstream language, but it works because Go has copy semantics — value receivers physically cannot mutate the original. TypeScript/JavaScript has no such distinction; everything is reference semantics. Therefore, the explicit modifier approach (`identity`/`mutator`/`links`) is the correct adaptation: it achieves the same semantic goal through declaration rather than mechanism.

## Summary: Go ↔ TypeScript-Go Correspondences

| Go Feature | TypeScript-Go Feature | Strength of Parallel |
|------------|----------------------|---------------------|
| Value receiver `(s Store)` | `identity` modifier | **Strong** — same semantic: "does not mutate" |
| Pointer receiver `(s *Store)` | `mutator` modifier | **Strong** — same semantic: "may mutate" |
| `sync.RWMutex.RLock()` | Narrowed identity read region | **Moderate** — shared reads, different scope mechanism |
| `sync.RWMutex.Lock()` | Mutator call (invalidates narrowing) | **Moderate** — exclusive write, different enforcement |
| `<-chan T` (receive-only) | `identity () => T` | **Moderate** — read capability |
| `chan<- T` (send-only) | `mutator (v: T) => void` | **Moderate** — write capability |
| Channel linking (send invalidates receive) | `links` clause | **Moderate** — explicit dependency |
| `comparable` constraint | `identity` as capability | **Weak** — different kind of constraint |
| `go vet` / `staticcheck` | Built-in CFA checks | **Weak** — tool vs language distinction |
| Type assertions / type switches | CFA narrowing (typeof, discriminants) | **Weak** — different narrowing targets |

The strongest parallel is value/pointer receivers. Go's design proves that distinguishing "this operation reads" from "this operation writes" at the method level is both practical and valuable — it's been core to Go's type system since Go 1.0 (2012). TypeScript-Go's `identity`/`mutator` system brings this same insight to a structural, gradual type system where copy semantics aren't available, using declaration-site modifiers instead.
